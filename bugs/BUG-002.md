# BUG-002: `--link-source` 가 Go 백엔드 핸들러 대신 frontend JS 클라이언트로 오링크 (케이스 구분 이름매칭 + lang 무관 파일수집)

## 테스트 환경

- **huma**: BUG-001 수정 반영 빌드 (VERSION `v0.1.4`, 커밋 `84596a1` "BUG-001 근본 수정", `make install`)
- **검증 대상 프로젝트**: `~/.clari/repos/fullend/yongol/examples/listmonk`
  - `manifest.yaml`: `backend.lang: go`, `framework: echo`
  - 스캔 입력 OpenAPI: `~/.clari/repos/codistill/files/listmonk-scan/listmonk-recovered.openapi.yaml` (142 operation). **각 operation 의 `handler` 명이 JS식 camelCase**(예: `createSubscriber`, `getSettings`).
- **링크 대상 소스**: 클론된 listmonk 레포(같은 디렉토리). 실제 백엔드 핸들러는 **`cmd/*.go` 의 PascalCase 메서드**(예: `func (a *App) CreateSubscriber(`), 동시에 **`frontend/src/api/index.js` 에 동명 camelCase 클라이언트**(예: `createSubscriber: (...) => http.post(...)`)가 존재하는 **다국어(polyglot) 레포**.
- 재현 명령: `huma scan --from <위 openapi> --link-source .`

## 증상

`--link-source .` 결과 엔드포인트가 **백엔드 Go 핸들러가 아니라 frontend JS 클라이언트로 매핑**된다:

```
Linked 70/142 endpoints to source under .
  → 그중 65개가 frontend/src/api/index.js 로 오링크
  → Go(cmd/*.go) 로 올바로 링크된 건 5개뿐
  → 72개는 미링크(UNVERIFIED)
```

`--link-source` 는 huma 가 UNVERIFIED 를 해소하라며 제시하는 1순위 처방인데, 그 결과가 **엉뚱한 파일(프런트 클라이언트)** 을 가리킨다. backend.lang 이 `go` 임에도 Go 소스를 우선하지 않는다.

## 원인

1. **`internal/scanner/find_handler_def.go` — 케이스 구분 + `:` 분기 매칭.**
   ```go
   defRe := regexp.MustCompile(`\b` + regexp.QuoteMeta(handlerName) + `\s*(\(|=|:)`)
   ```
   - **대소문자를 구분**한다. OpenAPI handler 명이 camelCase(`createSubscriber`)면 Go 의 export PascalCase
     `func (a *App) CreateSubscriber(` 에는 **매칭되지 않는다.**
   - 대안 `:` 가 **JS 객체리터럴 메서드 정의**(`createSubscriber: (...) => ...`)에 정확히 매칭된다.
   - 즉 같은 이름이 양쪽에 있을 때, 케이스가 어긋난 Go 는 놓치고 케이스가 맞는 JS 에만 걸린다.

2. **`internal/scanner/collect_source_files.go` — `backend.lang` 무관 전 확장자 수집.**
   ```go
   var sourceExts = map[string]bool{".go":true, ".py":true, ".js":true, ".ts":true, ...}
   ```
   `backend.lang: go` 여도 `.js`/`.ts` 를 후보 파일에 포함한다. 그래서 frontend 클라이언트가 매칭 후보로 들어온다.

3. **경로(path) 신호 미사용 — 이름 1개로만 매칭.** `findHandlerDef(files, handlerName)` 은 라우트의
   `(method, path)` 를 전혀 쓰지 않고 handler 이름만으로 첫 매칭 파일을 반환한다(`return f, line` on first hit).
   엔드포인트 path ↔ 라우트 등록부 매칭이 없어, 동명 후보 간 **백엔드/프런트 구분 근거가 없다.**

(참고: `filepath.Walk` 는 사전순이라 `cmd/` 가 `frontend/` 보다 먼저 방문되지만, **1번의 케이스 불일치로 `cmd/` 에서 매칭 자체가 0건**이라 첫 매칭이 결국 frontend JS 가 된다.)

## 영향

- **증거가 잘못된 코드를 가리킨다.** BUG-001 수정으로 `--link-source` 는 "응답 분기 분모(소스 ground-truth)" 를
  만드는 핵심 증거 경로가 됐는데, 그게 **실제 핸들러가 아닌 JS 클라이언트**에서 분기를 열거하면 CRI/커버리지
  근거가 무의미해진다(엉뚱한 file:line, 엉뚱한 분기).
- **polyglot 레포(Go 백엔드 + JS/TS 프런트)에서 사실상 사용 불가.** 사용자가 root 를 `cmd` 로 좁히고
  handler 명을 Go 식으로 맞춰 재작성해야만 정밀 링크된다(아래 우회).
- BUG-001 이 살린 정직성(UNVERIFIED)을 **거짓 링크가 다시 훼손**할 수 있다 — 미링크면 정직히 UNVERIFIED 지만,
  오링크면 잘못된 소스로 "링크됨" 처리되어 provenance 가 오염된다.

## 수정 방향

1. **`backend.lang` 으로 후보 확장자 한정/우선.** lang=go → `.go` 만(또는 우선) 수집. 최소한 backend 언어
   확장자를 다른 확장자보다 우선 매칭.
2. **경로 기반 매칭 병용.** handler 이름 단독이 아니라 라우트 `(method, path)` 를 1차 신호로 사용 —
   프레임워크 라우트 등록부(echo `e.GET(path, Handler)` 등)와 대조해 핸들러를 특정.
3. **네이밍 정규화 매칭.** camelCase ↔ PascalCase 등 케이스/네이밍 차이를 흡수(대소문자 무시 또는
   언어 관용 변환 후 비교).
4. **언어별 정의 형태 우선.** Go 는 `func ... Name(` 정의를, JS 객체리터럴 `name:` 보다 우선.
5. **오링크 경고.** 링크된 파일 확장자가 `backend.lang` 과 다르면 WARNING 으로 노출(예:
   `linked to .js while backend.lang=go`).

### 현재 우회(워크어라운드)
listmonk 라우트 등록부(`cmd/handlers.go` + `cmd/init.go`)에서 `(method, path) → Go 핸들러(PascalCase)` 를
직접 파싱해 각 엔드포인트 handler 명을 Go 식으로 교정한 뒤 `--link-source cmd` 로 재링크 →
**142/142 가 `cmd/*.go` 로 정밀 링크, frontend JS 오링크 0건** 달성. 즉 도구가 자동으로 해야 할 일을
사용자가 수동 라우트 파싱으로 대체해야 했다.
