# BUG-001: OpenAPI 로 scan 한 프로젝트에서 정적 응답 커버리지가 분모=1 로 부풀려져 100% 오표시 (소스 분기분석이 침묵 비활성화됨)

## 테스트 환경

- **huma**: v0.1.4 (`~/.clari/repos/huma`, `make install` 빌드)
- **검증 대상 프로젝트**: `~/.clari/repos/fullend/yongol/examples/listmonk`
  - `manifest.yaml`: `backend.lang: go`, `framework: echo`, live 모드(`testing.server.start: "docker compose up -d"`, `ready: "/admin/login"`, `build: "true"`)
  - `hurl/*.hurl` 142개
  - `.huma/session.json`: 142 엔트리
- **scan 방식**: `huma scan --from ~/.clari/repos/codistill/files/listmonk-scan/listmonk-recovered.openapi.yaml`
  - 입력 OpenAPI 는 codist 스캔→수동 복구본(142 operation). **엔드포인트당 응답 status 를 1개씩만 선언**(200×139, 302×3, 에러응답 미선언).
- **오라클(live)**: listmonk **v6.1.0**, 공식 docker 이미지 `listmonk/listmonk:latest` (계측 안 된 릴리스 바이너리), `http://localhost:9000`, 컨테이너 `listmonk_app` + `listmonk_db`
- **hurl**: 6.0.0

## 증상

`huma status` / `huma next` 가 **DONE 142/142 (100%)** 를 보고하지만, 이 "100%" 는 실제 응답 커버리지를
거의 측정하지 않은 **부풀려진 수치**다. 각 엔드포인트의 hurl 은 golden-path 단일 status(대부분 200)만
assert 하고 에러 분기(400/401/404 등)는 전혀 테스트하지 않는데도 커버리지가 100% 로 나온다.

`.huma/session.json` 실측:

```
total entries:            142
source 링크 있는 엔트리:   0    (전부 source:"")
엔드포인트당 선언 status:  전부 1개
선언 status 분포:          {200: 139, 302: 3}
```

즉 정적 커버리지의 **분모가 엔드포인트당 1** 이라, hurl 이 그 1개를 assert 하면 1/1 = 100% 가 공짜로 나온다.

## 원인

`cmd/response_branches.go` 의 `responseBranches()` 가 **`ep.Responses` 가 비어있지 않으면 즉시 반환**하고,
소스 분기분석(`analyzeBranches`)을 건너뛴다:

```go
func responseBranches(ep *scanner.Endpoint, lang string) []analyzer.ResponseBranch {
    if len(ep.Responses) > 0 {
        branches := analyzer.ParseResponses(ep.Responses, ep.Source)
        if len(branches) > 0 {
            return filterClientBranches(branches)   // ← OpenAPI 선언 status 만으로 조기 반환
        }
    }
    branches := analyzeBranches(ep, lang)            // ← ep.Responses 가 있으면 도달 불가
    return filterClientBranches(branches)
}
```

`huma scan --from <openapi>` 로 스캔하면 각 엔드포인트의 `ep.Responses` 가 OpenAPI 선언값으로 채워진다.
입력 OpenAPI 가 status 1개만 선언하면 `branches` = `[200]` 1개가 되고, 핸들러 소스에서 실제 return
분기(400/404/401…)를 열거하는 `analyzeBranches` 는 **영영 호출되지 않는다.**

- `cmd/filter_client_branches.go` 는 `Status >= 500` 만 제거하므로 분모를 늘려주지 못한다(200 은 그대로 1개).
- `internal/hurlcheck.CheckResponseCoverage` 는 `branches`(기대) 대비 hurl status 교집합으로 퍼센트를 낸다 →
  기대 `[200]`, hurl `[200]` → **covered 1 / total 1 = 100%.**
- `cmd/verify.go` static 모드는 `respResult.Missing` 가 비면 곧장 `MarkPass` → IMPROVE 신호 없음.

추가로, OpenAPI 로 스캔한 탓에 **엔트리에 `ep.Source` 링크가 없다**(session `source:""`). 따라서 설령
조기 반환을 제거해 `analyzeBranches` 로 떨어지더라도, 분석할 소스 위치가 없어 분기 열거가 불가능하다.
**OpenAPI 기반 스캔에서는 정적 분기분석이 이중으로 비활성화**되는 셈이다.

## 영향

- huma 의 핵심 가치(핸들러의 실제 return-status 분기를 열거해 **빠진 에러케이스 테스트를 IMPROVE 로 지적**)가
  `ep.Responses` 가 채워지는 **OpenAPI 주도 스캔의 일반적 경우에 침묵 비활성화**된다.
- 빈약한 OpenAPI(엔드포인트당 status 1개)를 입력하면 커버리지가 **항상 트리비얼 100%** 로 나와,
  "DONE/PASS 100%" 가 실제로는 golden-path 단일 status 만 검증했다는 사실을 **거짓 자신감**으로 가린다.
- live 모드 + 계측 안 된 이미지(docker)일 때 런타임 커버리지도 `Total==0` 으로 빠져 즉시 PASS 처리되므로,
  **정적(분모=1)과 런타임(Total=0) 양쪽 모두 무신호** → 사용자는 커버리지가 측정되는 줄 알지만 실측치는 사실상 0.
- 본 listmonk 사례에서 142/142 PASS 는 "스모크 통과" 는 정직하나 "커버리지 상당함" 으로 오독될 소지가 크다.

## 수정 방향

1. **분기 소스 합집합화 (핵심).** `responseBranches()` 가 `ep.Responses` 에서 조기 반환하지 말고,
   **OpenAPI 선언 분기 ∪ 소스 분석 분기**를 status 로 dedup 해 합치도록 변경. 빈약한 OpenAPI 가
   소스 분기분석을 억제하지 않게 한다. (`ep.Source` 가 있을 때 `analyzeBranches` 를 항상 병행.)
2. **소스 링크 확보 경로 제공.** `huma scan --from <openapi>` 로 들어온 엔드포인트도 가능하면
   핸들러 소스에 매핑(이미 codist 가 file:line 을 추출 가능)하거나, OpenAPI-only 스캔 시
   "소스 미링크 → 분기분석 불가" 를 **경고(M-xx)** 로 노출.
3. **분모 투명화.** `huma status`/PASS 프롬프트에 커버리지의 **분모(기대 status 개수)** 를 함께 표기해,
   분모=1 의 100% 가 thoroughness 로 오인되지 않게 한다. (예: `PASS (1/1 declared status; source branches: n/a)`)
4. (선택) OpenAPI 선언이 2xx/3xx 단일뿐이면 **클라이언트 에러 분기(400/401/404)를 소스에서 보강 권고**하는
   IMPROVE 힌트 추가.
